파일 트리 UI는 보기보다 까다롭다. 폴더를 접고 펼치는 것까진 쉬워 보여도, 실제 제품에 넣으려면 검색, 끌어다 놓기, Git 상태 표시, 많은 파일 수에서의 성능, 키보드 탐색 같은 요구가 금방 붙는다.

[@pierre/trees](https://trees.software/)는 이런 문제를 겨냥한 라이브러리다. 이름만 보면 그냥 트리 컴포넌트 같지만, 실제로는 **파일 탐색기 같은 경험**을 만들기 위해 필요한 구조를 꽤 잘 갖춰두고 있다.

## 이 프로젝트가 뭔가

`@pierre/trees`는 웹에서 파일 트리를 렌더링하기 위한 라이브러리다. React에서 쓸 수 있고, 필요하면 순수 자바스크립트나 SSR 흐름까지 확장할 수 있다. 공식 README 기준으로도 React, 순수 자바스크립트, SSR, 웹 컴포넌트용 진입점이 따로 나뉘어 있다.

즉 단순히 “트리 하나 그려주는 React 컴포넌트”보다는, 파일 트리라는 UI를 제품에 넣기 위한 기반에 더 가깝다.

## 어떤 문제를 해결하나

이 라이브러리가 해결하려는 문제는 꽤 명확하다.

첫째, 파일 트리는 일반적인 트리 뷰보다 상호작용이 많다. 선택 상태, 포커스, 검색 결과, 이동 대상, 이름 변경 대상이 서로 어긋나지 않아야 한다.

둘째, 파일 수가 많아지면 렌더링 비용이 빠르게 커진다. 작은 데모에선 괜찮아도 실제 저장소나 워크스페이스를 다루면 금방 무거워진다.

셋째, 제품에 붙이려면 단순 렌더링만으로는 부족하다. Git 상태 표시나 컨텍스트 메뉴, 끌어다 놓기, 키보드 탐색처럼 파일 탐색기다운 기능이 같이 필요하다.

`@pierre/trees`는 바로 이런 현실적인 요구를 한 덩어리로 다룬다.

## 어떤 기능을 제공하나

공식 사이트와 문서 기준으로 보면 핵심 기능은 이 정도다.

- React / 순수 자바스크립트 / SSR / 웹 컴포넌트 지원
- 검색 필터
- Git 상태 표시
- 끌어다 놓기
- 컨텍스트 메뉴 조합
- 키보드 탐색
- 큰 트리를 위한 자동 가상화(virtualization)
- CSS 변수 기반 커스터마이징
- 경로 중심(path-first) 상태 모델

특히 사이트에서는 수만 개 항목도 가상화(virtualization)로 빠르게 다룰 수 있다고 설명하고, 문서에서는 `preparedInput` 같은 구조를 통해 큰 트리 데이터를 미리 준비하는 흐름도 안내한다.

## 뭐가 더 좋은가

내가 보기엔 이 라이브러리의 장점은 기능 개수보다 **문제 정의가 정확하다**는 데 있다.

보통 트리 컴포넌트는 “계층형 데이터를 보여준다” 수준에서 끝나는 경우가 많다. 그런데 `@pierre/trees`는 처음부터 파일 트리라는 특수한 UI를 전제로 둔다. 그래서 선택, 포커스, 검색, 이름 변경, 이동 같은 동작이 모두 표준 경로(canonical path)를 기준으로 이어지도록 설계했다.

이게 꽤 중요하다. 파일 트리에서는 화면에 보이는 이름보다 “이 경로의 파일이 지금 어떤 상태인가”가 더 중요할 때가 많기 때문이다. 공식 문서가 경로 중심(path-first) 모델을 강조하는 이유도 여기 있다고 본다.

또 하나는 성능을 옵션처럼 뒤에 붙이지 않았다는 점이다. 가상화(virtualization)와 `preparedInput` 흐름이 문서 전면에 나와 있어서, 작은 데모뿐 아니라 실제 저장소 규모까지 염두에 두고 있다는 인상이 강하다.

## 다른 것과 비교했을 때 탁월한 점

정리하면 `@pierre/trees`의 탁월함은 아래에 있다.

### 1) 그냥 트리가 아니라 파일 트리에 특화돼 있다

범용 트리 컴포넌트보다 파일 탐색기 경험에 더 가깝다. 그래서 Git 상태 표시, 끌어다 놓기, 검색, 컨텍스트 메뉴 같은 기능이 자연스럽다.

### 2) 상태 모델이 일관적이다

문서에서 경로 중심(path-first) 모델을 강하게 밀고 있는데, 이 덕분에 선택, 포커스, 이동, 이름 변경 같은 상호작용이 한 언어로 묶인다. 제품 코드에서 다루기 편한 방향이다.

### 3) 규모가 커졌을 때를 미리 생각했다

가상화(virtualization), `preparedInput`, SSR 흐름까지 제공한다. 단순히 예쁜 데모를 보여주는 수준보다 한 단계 더 현실적이다.

### 4) 커스터마이징 방식이 비교적 현실적이다

섀도 루트(shadow root) 안에서 렌더링하면서도 CSS 변수를 주요 스타일 표면으로 제공한다. 외부 CSS 충돌을 줄이면서도 커스터마이징은 열어둔 방식이다.

## 언제 잘 맞을까

이 라이브러리는 이런 경우 특히 잘 맞아 보인다.

- 코드 브라우저
- 저장소 탐색기
- 문서/콘텐츠 파일 구조 뷰어
- IDE 스타일 사이드바
- 많은 항목을 가진 프로젝트 탐색 UI

반대로 아주 단순한 계층형 메뉴 정도라면 조금 과할 수도 있다. 이건 범용 트리라기보다 **파일 중심 상호작용**에 더 잘 맞는 도구에 가깝다.

## 마무리

`@pierre/trees`는 React용 파일 트리 UI가 필요할 때 꽤 먼저 검토해볼 만한 라이브러리다. 무엇보다 “트리 컴포넌트”가 아니라 “파일 탐색기 경험”을 만들려는 방향이 분명해서 좋다.

검색, 상태 표시, 이동, 대규모 데이터, 커스터마이징까지 함께 고민해야 한다면 더 눈여겨볼 만하다. 소개 페이지는 간결하지만, 문서와 README를 보면 생각보다 꽤 단단하게 설계해둔 프로젝트다.
